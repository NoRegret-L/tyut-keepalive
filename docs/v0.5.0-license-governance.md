# Dependency and license governance (review, not release approval)

Related: #3. This workflow is independent from Development CI and release workflows; it never publishes, signs, or creates tags. Tools are pinned to released cargo-deny 0.22.1 and cargo-about 0.9.3, installed with their own locked dependencies. No application dependency or lockfile changes.

## Scope

Four distribution targets: Windows x64, Linux x64, macOS Intel and Apple Silicon. For each, cargo metadata --locked --filter-platform and cargo tree --locked --target record default-feature resolution, normal, normal/build, normal/build/dev, and feature edges. These are static graph views, not exact linked or bundled artifacts; build scripts can introduce native or generated content. Cargo.lock can include optional dependencies not actually compiled. NPM lock inventory is metadata only.

## Two independent checks

- cargo-deny: preliminary conservative permissive SPDX baseline, not a maintainer-approved license policy. Does not ignore private crates or override expressions; MPL-2.0, Unicode-3.0, CDLA-Permissive-2.0, exception expressions and other unreviewed terms remain visible as failures where applicable. PR #8 adopted MPL-2.0 for project-owned source. The sole package-specific exception is for tyut-keepalive at exactly 0.5.0; MPL-2.0 remains disallowed globally and all third-party rejections remain visible. No other license approval is implied. The result is intentionally non-green if terms are outside the provisional list. No continue-on-error, no advisory ignores. Existing dual RustSec audits are unchanged.
- cargo-about: separate candidate license-text collection list includes currently observed conditional licenses so they can be examined, not approved. The tool runs on a disposable git archive; only application publish=false is set there to exclude it from third-party notices, not from cargo-deny. It uses --locked --fail and includes build/development dependencies. If harvesting fails, retain the error log and fix with upstream-supported evidence-based clarifications rather than invented hashes or reduced detection thresholds. A successful report is not an approved distribution notice. Do not ship the draft artifact.

## Evidence

Workflow artifacts contain per-target metadata and trees, npm lock inventory, lock hashes and license scope, candidate text and logs. The maintainers authorized MPL-2.0 for project-owned source in PR #8; see LICENSING.md. Governance CI does not change the production manifest or publish metadata. Before release, independently review application authorization, MPL source access/notice obligations, Apache NOTICE and copyright text, native GTK/WebKit and system library terms, cryptography/certificates, npm, assets/fonts and exact installer content. Add approved policy and packaging of reviewed notices only in a subsequent PR. Real installation/signing tests and all other #3 gates remain required.

## Conditional approval and local package proof

Both maintainers' approval of the exact 25 rejected versions was reported in chat. license-approvals.json records the evidence baseline; deny.toml retains the prior global list and only adds exact package exceptions. No blanket approval. stage_license_notices.py fails if these records disagree, checks generated text coverage (including the mixed Unicode AND requirement and LLVM exception), verifies original crate bytes against Cargo.lock, and copies original notice files for these crates, vendor dependencies and installed npm runtime packages.

The staged bundle-resources folder contains THIRD-PARTY-LICENSES.txt (the conservative cargo-about candidate, including build/dev dependencies), LICENSE and LICENSING.md, original notice files, SOURCE-ACCESS.md/JSON, a git archive of the exact checked-out source and five original MPL .crate archives. SHA256SUMS binds every staged resource. All source archives are locally available alongside the notices, not dependent on an expiring Actions URL. The source archive contains vendored patches and build configuration; exact production distribution source must be generated from the actual shipped checkout.

An independent Linux DEB smoke job uses a generated Tauri resource-map overlay, extracts the unsigned package and compares every resource byte. It does not upload an installer or modify the production configuration, release jobs, or updater security. Windows MSI, macOS DMG, AppImage, native system libraries, assets, exact binary linkage and final notices remain independent review gates. Do not publish this CI test package. Before authorizing a release, integrate the reviewed resources into the official and independent test build paths and verify their actual installer contents on every supported format. Existing RustSec audits are unchanged.
